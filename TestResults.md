# Manual Dice Roller standalone 0.8.4.2 — verification and qualification

This is a candidate for live Windows single-player and multiplayer testing. The runtime DLL is built against the supplied pristine Solasta Unity/.NET Framework files and genuine pinned Unity Mod Manager/Harmony dependencies. Developer fixtures run under Linux/.NET 8. A developer pass does not certify live Unity Mono rendering, scheduling, Photon delivery or gameplay. Actual production and multiplayer qualification are recorded separately in `release-qualification.json`; without accepted live evidence, both remain false.

## 0.8.4.2 changes reviewed (fifth live session)

- **Live evidence.** The fourth session's pauses came from one roll setting that differed on the client. The client's log shows "Manual dice profiles or room rosters do not match." at each of the five handshakes. After the players matched it, one session ran from readiness to the end: 264 roll descriptions and results (721 rendezvous, 98 entered faces). These matched on both computers in random state, characters, health and native results. There were no pauses, game exceptions or mod errors. Shared steps without entered dice took a median 0.3 s (90th percentile 0.35 s). Three descriptions (a Giant Crow talon attack's save and damage, and a spell's save) differed only in their effect forms.
- **Cause.** `EffectForm.Copy` takes damage forms from a pool through `DamageForm.GetCopy`, and `DamageForm.Copy` does not copy or clear `damageBonusTrends`. That list is the tooltip breakdown read by `GuiEffectsFormater` only. A reused pooled form therefore keeps an earlier local breakdown, whose history differs per computer.
- **Change.** The descriptor no longer writes `DamageForm.damageBonusTrends`; every other damage form field is still compared. The descriptor suite adds a case: the same form with a leftover breakdown matches, while a different damage bonus still differs and is named. The case fails without the change.

## 0.8.4.1 changes reviewed (fourth live session: repeated pauses while loading)

- **Live evidence (host log only).** The host's 0.8.4.0 sessions with the second player each stopped 0.1-1.5 s after `session_joined`, before any `session_ready` or roll: once in the lobby, then again after each location load (four rearms). Each time the reason was "A room member stopped the synchronized multiplayer roll." with no detail. The client stops on the host's first hello when its profile (mod build, game, loader and the shared roll settings) differs, before the host has read the client's hello. So only the client knew why.
- **Change.** A halt packet already carries the digest of its reason. Receivers now map known reasons, those of this and earlier builds, back to text and report "Another player's game stopped manual dice: <reason>". A profile mismatch records both profiles in `detail`. A room-member mismatch has its own reason. The pause notice for a mismatch reads "MANUAL DICE OFF: versions or roll settings differ". The same reason is noticed at most once per ten minutes, rather than at every reload. The settings panel explains what must match. Wire protocol unchanged (2).
- **Tests.** The protocol suite checks that every peer of a mismatched room reports a mismatch, that the detecting peer logs both profiles, and that a two-player version mismatch is named on the host. It also checks that an unknown reason keeps the generic report and that known reasons map from their digest.

## 0.8.4.0 changes reviewed (after the third live two-player session)

- **Live evidence.** With 0.8.3.0, both computers completed 223 shared rolls (625 rendezvous) in a custom campaign without a pause. Every description and result matched in random state, characters, health and return values. Eight steps differed only in `attackMode`/`attackMethod` (one of two wolf variants: same name "Attack_Wolf_Bite", different hash) or in the effect forms of an attack's saving throw. Both games also logged the same animation timeout at the same point.
- **Cause.** `UserCampaign.LoadUserMonster`, `LoadUserItem` and the other user-content loaders call `SetUserContentGUID(Guid.NewGuid())`, so a custom campaign's definitions get a different GUID on each computer. The descriptor wrote each definition's name and GUID. The game's network references (`SerializeDatabaseReferenceForNetwork`) use the name only, and the descriptor now does too (conditions included). The earlier live attack-mode differences were in the same campaign.
- **Prompt context (display only).** A post-planning pass (`RollReasons`, called from `PlanTarget` for every planned native call, composite parts included) explains saving throws: the source (attacker and attack, caster and spell, trap), and from the applied effect forms what a success changes. That covers half or no damage, a condition avoided (or ending, for a condition the target already has), forced movement, and what applies either way. It also names an attack's weapon and target. Damage prompts name their target and say when the game halves the total. A trap's damage dice, planned before the target's save is known, carry a hint that reads the save's entered face (`HintAfterSave`). Concentration names the spell kept and the damage taken. Death saves and initiative explain the roll. No text enters a signature or the multiplayer agreement.
- **Tests.** A new `roll-reasons` suite runs the explanations over genuine game records (attack-mode save, halving trap, negated damage and a held condition, localized titles, untouched bonus dice and unreadable forms, attacks). The descriptor suite adds a per-computer GUID case (same named attack, different GUIDs: same description; renamed attack: still differs and named). The runtime suite adds the save-dependent damage hint.

## 0.8.3.0 changes reviewed (games kept in lockstep)

- **Cause.** Solasta's multiplayer is a tick lockstep: `NetworkingManager.FixedUpdate` advances one tick per fixed step while `NetworkTick.UpdateTimeManipulation()` is positive, runs the commands scheduled for that tick, and the gameplay managers run only through `NetworkingDefinitions.CanUpdate()` (multiplayer: a fixed step with gameplay not frozen). Action RPCs execute at a scheduled tick and resolve the attack mode as an index into the acting character's list at that tick. Through 0.8.2.0 the mod held the owning action coroutine while players decided a roll, but ticks kept counting; each computer released it at a different tick, so later scheduled actions ran against differently progressed games (the attack-mode differences in both live sessions).
- **Fix.** A postfix on `NetworkTick.UpdateTimeManipulation` (IL pinned, owner-checked) reports a stopped tick while a shared roll is pending: from the native run that reaches it, through the decision, and again from the native call through the completion comparison, and while multiplayer deferred rolls are queued. The decision is pumped once per rendered frame outside the game coroutine (`NetworkGate`/`PumpNetwork`); the coroutine claimed at the await is recorded and bound explicitly. The game coroutine always resumes at a later tick, so every computer runs the native call at the next tick. Ticks resume only when `UpdateTimeManipulation` runs inside a fixed step (`Time.inFixedTimeStep`), never in the per-frame recompute between steps, so the first tick after a roll is the same whatever the frame timing or script order.
- **Related rules.** A game random draw inside a fixed step is lockstep and no longer pauses manual dice; outside the ticks it still does. A deferred roll reached outside the owner's run while another shared step is pending keeps the game's dice (queued, it would wait on a step that needs a tick). A canceled wait ends at the next frame and never leaves the ticks stopped. Paused or offline play never stops ticks.
- **Tests.** The scheduler suite runs the postfix on the pristine `NetworkTick` (stopped while pending, held through frame recomputes, resumed only at a fixed step, cleared by reset, never stuck when the fixed-step answer is unavailable) and checks in-tick and out-of-tick draws. The runtime suite asserts that no native call runs in the tick that reached it, that the ticks stay stopped over a multi-frame decision and completion, deferred freezing, and cancellation. The connected-process suite now models game ticks: each peer runs a random 0-3 fixed steps per frame through the production postfix, steps start at ticks fixed by the previous step, and other gameplay draws game dice every tick in new `lockstep` rooms (two, three and four peers, and gameplay-before-tick order). Every shared roll ran at the same tick after the same other gameplay with the same resulting state on every peer. A control room that ignores the stopped ticks (the 0.8.2.0 behaviour) diverged on every step, so the check is not blind.

## 0.8.1.0 changes reviewed (after the first live two-player session)

- **Live evidence.** Both players' 0.8.0.0 Windows logs agree on 48 shared steps (surprise, identification, initiative, wolf attacks, a save and damage, and a manually entered Sleep pool). At step 49, a wolf's attack, both computers had the same site and owner but different descriptions. The host halted, the mod left the room, and an exception thrown into the game's action coroutine made Solasta show "Mod Warning! … instability". See `Source/audit/network/NATIVE-NETWORK-REVIEW.md`.
- **Descriptor cause, reproduced.** When `CanAttack` cannot confirm an attack locally, the game rolls with the attack modifier the acting player's game sent. `TrendInfo`'s network serializer drops non-character sources, the die flag and the die type. The old descriptor compared them, and its failure on the new case is kept in `Source/tests/network-descriptor/regression-before-network-copy.txt`. Descriptors now use the game's network-serialized trend fields, the game's network identity of an attack mode and the serialized action parameters. Bless/Bane dice are found from the attacker's combat affinities instead of the dropped die flag.
- **No kick, no game exception.** A plan-only difference (same native call and random state) lets the game roll that step for everyone. Any real disagreement pauses manual dice: no `LeaveRoom`, no held coroutines, no exception in a game coroutine or patched native method; the pending roll uses the game's dice, and a 20-second notice appears. A location load or a roster/profile change starts a fresh session.
- **Diagnostics.** `roll_descriptor` log lines with per-part hashes; the `halted` line carries both players' descriptions.
- **Tests.** The connected-process suite adds a `different-plan` room (a plan-only difference falls back without pausing). Its four failure rooms now require every peer to pause, stay in the room, never break the native coroutine and finish the schedule with the game's dice. The descriptor suite adds network-copy, attack-mode, action-parameter and diagnostic-part cases. The runtime, scheduler, transport, coverage, sync-sites, effects-native, ui-render and ui-input-boundary cases cover pausing, released holds, re-arming, received Bless trends and the longer notice.

## 0.8.0.0 changes reviewed

- **Plan features.** Conditional dice groups (asked only when an earlier entered face means the game will roll them), ready actions (applied once every face is known and agreed, before the original resumes) and game-master dice (enemy/NPC dice not tied to a player's character; host-entered in multiplayer). Spell effect proxies resolve to their controller for settings, prompts and multiplayer ownership.

- **Traps and hazards (new setting, fingerprinted).** `FunctorEnvironmentEffect.Execute` is replaced by an equivalent iterator that captures the private trigger, waits for each target's save and the damage dice, then runs the captured call in its own native step; nothing waits when no die is manual. - **Other new rolls.** Dispel Magic checks (`ApplyCounterForm`), the Bardic penalty die when a condition lands (`OnConditionAdded`), an item's last-charge d20 (`UseDeviceFunction`), monster power recharge and Confusion-style behaviour dice at turn start, noisy-object Stealth (`FunctorStealthBreaker`), the creatures' ambush d20 and food-yield dice. Each replicated method is pinned by IL hash.
- **UI.** Colour-coded roll kinds with badges, larger text and running totals, a roll history panel, a multiplayer waiting banner naming the rolling player, settings presets, folding sections and one-line descriptions. UI-only settings are excluded from the multiplayer fingerprint.
- **Tests.** `sync-sites` grew to 59 cases (recharge, behaviour, ambush, food yield, trap parts against the original trigger, trap capture and immediate resolution, hazards, noisy objects, last charge). `effects-native` gained traps, dispel, Bardic penalty, Bless/Bane, proxy controller, conditional and master dice cases with the pristine dispatcher. ## 0.7.0.0 changes reviewed

- **Start of a battle turn.** `GameLocationBattle.NextTurn` and `StartFirstTurnOfRound` are transpiled so that `StartBattleTurn` can be deferred together with the pinned remainder of the method (death check, next-turn recursion, `TurnInitialize` state change). Start-of-turn condition saves, recurring condition forms and lingering global/light effects are planned as composite parts in the original order; nothing inside a natively started turn is deferred. The tail transpilers were applied to the pristine methods under real Harmony and the replayed tail was compared with the original's branches.
- **Composite plans.** A deferred call that makes several native rolls is planned part by part with the ordinary planners. Each part's dice are bound to its anchor (the condition or effect being processed), static bonuses are gated to their part, and a mismatch retires that part's dice to the game. Replicated native logic is pinned by IL hash and refused if the game differs.
- **Lingering effects and recurring damage.** Area effects applied on entry or at the end of a turn and end-of-turn recurring condition forms are deferred with the target's save and every form die; the planned parameters match the arguments the original passes to `TryRollSavingThrow` and `ApplyEffectForms`.
- **Damage-triggered saves (optional).** `ProcessConditionsMatchingInterruption` is deferred with each `RollSavingThrow` the loop makes, in order. Off by default.
- **Spells with extra forms.** Effect batches whose dice forms are of one kind are planned even when they also contain condition, motion or other forms without dice. Batches mixing damage with healing, repeated form objects and random/filtered batches stay native. A new effects-native case runs the pristine dispatcher with motion forms around a damage form.
- **Features.** Deflect Missiles (new await site), spell failure (an original-equivalent iterator that waits before the pinned check) and spell slot preservation (new outer site that skips casts without a roll) use the raw-die hook only inside their own native step.
- **Stealth, Insight, travel crafting and hidden objects.** Stealth after a revealing action (new outer site) and at turn end plan the detectors' Perception (enemy dice only when enabled) and the hidden character's Stealth as composite parts; Insight profiling resolves through the dialogue site; travel crafting is probed and replayed as composite parts; the optional hidden-object Perception replaces the original loop with an equivalent one that waits before each roll.
- **Character screens (single-player).** Ability scores at character creation and optional rolled level-up hit points. Neither runs while networked.
- **Multiplayer.** Every new synchronous roll uses the deferred runner; new outer sites skip unresolved calls before any protocol exchange. The profile fingerprint includes all seven new settings.
- **Tests.** `sync-sites` grew to 50 cases (turn start and tail replay, lingering effects, recurring forms, interruption saves, composite anchors, stealth, profiling, travel crafting, features, hidden-object Perception and the character screens). The await, coverage, native and effects-native suites cover the three new await sites, the composite anchors and the relaxed effect batches.

## Completed implementation review (carried forward from 0.4.0.1)

The review retains original native action methods and dice evaluation. Manual values replace only the registered native face consumption after the corresponding action coroutine yields. Native modifiers, critical rules, traits, rerolls, target filtering, healing/spending and notifications remain in their original methods.

- Existing supported attack, initiative, death-save, action ability, save/retry, pure effect and rest paths remain covered by the regression inventory.
- Bardic Inspiration now has registered reaction boundaries for attacks, failed saves and failed ability checks. The reaction decision occurs before prompting; the source condition and native die must still match when the original roll resumes.
- Shove contests now use a read-only preview of the original wrapper and registered upstream await. Native skill selection, advantage/modifiers and both original contest rolls remain in the game; random preview bonuses remain outside this bounded adapter.
- Replicated rest hit dice have a registered native asynchronous networking boundary. Native RPC/local-command ordering and the game's healing/spending/callback work remain in the original continuation.
- Multiplayer negotiates exact artifact/game/settings profiles and participant ownership before a manual action can commit. Every participating peer receives the same descriptor and ordered face vector, crosses matching barriers and advances the original native action.
- The deterministic native coroutine scheduler holds unrelated action work while a replicated roll is pending and compares resulting native state before releasing the next action. A missing/mismatched peer, stale packet, invalid owner, descriptor mismatch or unsafe session change blocks the coordinated action rather than accepting unverified manual data.
- Each registered native call captures its actual original return value and by-reference outputs before leaving the native scope. Multiplayer completion requires this observed result and compares it alongside inspected actor/condition attributes and deterministic random/luck state. This detects differences in native check outcomes and success deltas; it does not checksum the entire game world.
- Native banter updates are deferred during a held multiplayer roll. Guards stop unowned deterministic draws before shared game RNG advances while preserving native lock-flag randomness behavior.
- Face ownership remains bound to a native action and descriptor. Accepted/manual values cannot be reused by a different actor, feature, effect form or later action. Original native RNG consumption remains subject to the adapter's native execution/parity tests and live acceptance.
- Canceled multiplayer admission releases its exact owned native scheduler claim before a fresh session can proceed. The retained earlier failure evidence is `Source/tests/network-native/runtime/regression-before-claim-release.txt`.
- Controller changes are checked while waiting, during manual/Auto callbacks, after input and immediately before native execution, including automatic fallback. A changed or unverifiable owner stops the room, closes the exact owned UI and prevents a stale continuation from consuming dice. The previously failing transport case is retained in `Source/tests/network-transport/regression-before-controller-transfer.txt`.
- Wire version 2 binds all bootstrap acknowledgements to a fresh participant nonce, exact roster/profile and host session. A newly joined peer rejects a complete old bootstrap transcript and replaces only a provisional stale binding when the current host speaks. The previously failing protocol case is retained in `Source/tests/network-protocol/regression-before-stale-bootstrap.txt`.
- Enabled/disabled peers advertise different profiles. Startup advertises the final enabled state only after installation and UI creation; failed initialization still rolls back independently. The old ordering failure is retained in `Source/tests/plugin-lifecycle/regression-before-enabled-profile.txt`.
- The new connected-process suite runs the production protocol, transport, facade, broker, native adapter and scheduler together against copied pristine dice/RNG IL. Separate two- and four-player rooms verify manual and Auto outcomes, owner-only prompts, Lucky/advantage, Sleep, damage rerolls, static bonus dice, synchronous concentration, ordinary/Karmic sampling, exact draw counts and the next automatic roll. Mismatched profiles/controllers, pending transfers and differing native results must halt every peer at the appropriate boundary.
- Prior regression fixes cover failed Counterspell continuation states, exact native iterator cleanup, read-only scratch reference isolation, mutable reroll/provider state, bounded broker/plan inputs, rest UI rebinding and modal/input teardown.

## Build, tool and archive checks

`Build.py` snapshots runtime/audit source bytes, compiles against pristine game framework references, verifies all assembly/member identities, pure IL architecture, every Harmony registration/injection and negative binding fixtures, and reads original native IL through the real Harmony library. The game-provided Photon PUN, Realtime and client DLLs have independent checksum pins, metadata ABI checks and a genuine compile-time smoke witness. No connection is made by the build.

The release policy suite tests stale/missing runtime sources, tools, artifacts, audit/suite results and logs; non-Mono/old process markers; absent or incomplete actual acceptance; missing/mismatched multiplayer session/room/profile/actor/action/owner/vector evidence; native RNG/callback baseline disagreements; and unsafe Windows archive names/case collisions. The official PowerShell grammar parser checks every shipped `.ps1` without executing it. Windows PowerShell 5.1 behavior remains a live acceptance requirement.

The regression and release gates also verify all **20 shipped fixture manifests** against their recorded source, boundary and result hashes, including exact generated class slices. Packaging rejects stale or missing fixture evidence before publication and rechecks its captured bytes. The save fixture refreshes its successful pre/post provenance and explicitly identifies the generated `NativeInvocation` prelude as the only compiled portion of `RuntimeRolls.cs`.

Archive publication writes a temporary ZIP, verifies CRCs and exact checksums, and then replaces the destination atomically. Failure tests cover write/CRC/checksum/sharing errors, preservation of an existing archive and deterministic repackaging. The package contains exactly one runtime DLL and no game, Photon, loader, Harmony, GoDice, compiler, decompiler or test binaries. A production archive additionally retains only the accepted explicit evidence files and logs.

## Supported scope and remaining boundaries

Manual multiplayer requires every room peer to run the exact matching candidate and supported game/settings. A missing or mismatched mod is not a supported mixed-room configuration. Follow the runtime's guarded recovery status for disconnect/rejoin/roster/master changes; a fresh matching session may be required. Seamless migration and live Photon reliability must not be claimed from packet simulations.

The coverage review is mechanism based. Complete Unity spell/power assets and actual scene state were not supplied, so no claim is made that every spell definition or mod combination has been executed. Supported damage/healing/temporary-HP and HP-pool paths preserve native dice counts and target handling. Saves triggered by damage taken while a turn starts natively, Relentless-style knock-out saves, rage-end exhaustion saves, save rerolls when a condition is gained, random condition durations, regeneration amounts, unsafe Diamond Soul retry capture blocks and damage-with-healing/random/filtered effects retain their native behavior. With **Use these in multiplayer too** off, the synchronous extras also stay native while networked. Attack modifiers other than combat-affinity dice and Bardic uses inside a death save also remain native. Read `Source/audit/coverage/COVERAGE-REVIEW.md` for exact limitations. Unfinished Business is refused; external rule/patch combinations are not certified.

Developer UI fixtures cannot prove live appearance, physical drag/cursor reliability or actual frame timing. Native service-dependent Kindred sharing and complete final resistance/concentration/HP behavior need live acceptance.
