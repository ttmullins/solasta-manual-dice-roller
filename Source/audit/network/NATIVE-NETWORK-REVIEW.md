# Native networking review

Primary evidence is the supplied pristine `Assembly-CSharp.dll`, SHA256 `a87e45cbd187e42e9d64a610850b39edba4896168b14d71ca71c5d32cf9e96ee`, and its pinned Photon/Unity dependencies. This review derives behavior from original IL and does not assume the legacy modified game files are authoritative.

## Native replication and identity

| Path | Native behavior | Manual integration requirement |
| --- | --- | --- |
| Actions and action chains | `NetworkingManager` sends RPCs to `RpcTarget.AllViaServer`; each peer executes the same local action service | Every peer must reach an identical await boundary and agree on the original call descriptor |
| Initiative and death saves | Original battle coroutine and state machine drive native rolls | Use original iterator occurrences and original actor GUIDs; do not make a local UI-only request |
| Reactions | Reaction request decisions are replicated and validated actions execute through the original action service | The controlling character's owner supplies the face; all peers use the same accepted vector |
| Short-rest hit dice | `RollHitDieRPC` schedules `RollHitDieAsync`; every peer spends the die through `LocalCommandManager.RollHitDie` | Await the replicated coroutine call, not the initiator's `HitDiceRestItem` callback |
| Rest callbacks | Only the initiating peer recovers the stored UI callback | Preserve native callback locality while all peers spend and heal identically |
| Actor ownership | `IPlayerControllerService.GetPlayerControllingHero(RulesetCharacter)` returns a controller dictionary key; human controllers correspond to Photon actors | Validate the owner against current membership; substitutes use their original hero; non-human rolls use the host |
| Tick scheduling | Native delayed commands execute at a shared target tick; `NetworkingDefinitions.CanUpdate` restricts online gameplay to unfrozen fixed ticks | Do not use a later local render-frame tick as a persistent roll identity |

`CharacterActionParams` has no persistent `LocalId` or GUID. `CharacterActionChainParams.LocalId` and action callback IDs address initiator-local callbacks. They cannot independently identify a roll across peers. Process-local object hashes and broker generations are also unsuitable network identities. Canonical descriptors use verified site identities, actor/effect GUIDs, ordered occurrences, original value arguments, and stable feature values.

The replicated rest await is `NetworkingManager+<RollHitDieAsync>d__194`, call offset `0x004c`. Original `MoveNext` SHA256 is `8794555e58e10191a8ccb0efaa4d5ebaa17ba8e5e9c4c4ee417f7a175e15bcff`.

## Deterministic random state and scheduling

`RuleDefinitions.RollDie(DieType, AdvantageType, out int, out int, float)` calls native deterministic randomness once per raw face. Karmic draws use a floating random sample once per face. The game restores its stored `RandomSeed` and four-word `RandomState` before each deterministic sample, then records the new state. Unrelated local Unity random calls therefore do not alter deterministic game rolls when the native deterministic lock flags are empty.

An accepted multiplayer face advances the original native raw-draw routine using its original die, advantage, and alteration score, then preserves the agreed manual faces for the original actor rules. Native clamps, Lucky rerolls, forced damage, notifications, critical counters, and luck updates remain in the original code. Synchronization stamps include the exact stored random words and seed, exact `DiceLuckScore` float bits, `LastCriticalCounter`, randomness mode, and forced-critical setting.

Original `TA.Coroutine.Run` can progress multiple nested iterators before returning at a natural yield. The scheduler admits only the owning coroutine while a replicated roll waits. The verified native call captures its original return value and each by-reference output before leaving its scope. Its postfix reports completion after the original native continuation reaches the next yield or finishes. Every coroutine is held until peers compare native completion, including those observed return/output values. The Photon callback/update pump remains active. A failed session holds native gameplay until room departure.

Not every deterministic caller runs in a TA coroutine. In particular, `GameLocationBanterManager.UpdateImpl` also calls `UpdateBanterPools`, which draws cooldown values during exploration. Its entire native update is deferred during the hold. Guards on both native `DeterministicRandom.Range` overloads and `get_value` reject an unrelated deterministic draw before it advances shared game state. Cursor/AI/bestiary lock-flag draws retain their original global Unity randomness behavior.

Native background timing and render/animation paths still require actual two-player gameplay acceptance. A detected disagreement closes the manual session instead of silently proceeding with divergent state. In particular, live tests must include long exploration prompts with banter enabled, simultaneous actions, and leaving/rejoining a session.

## Dependency qualification

The game reserves Photon custom event 10 for its view setup; PUN has its own internal events. The transport selects a separately audited unused custom event, reliable delivery, no event caching, a protocol magic header, sender validation, and room membership checks.

CoreCLR cannot provide Unity's native InternalCalls. Genuine scheduler tests execute original TA coroutine behavior, and the complete five-target scheduler installation is additionally qualified against a test-only Unity dependency whose InternalCalls throw if invoked. The original main game assembly remains byte identical. This establishes generated patch compatibility without claiming native Windows gameplay evidence.

## 0.4.0.1 controller, bootstrap and integration review

The previous facade captured ownership only at admission. A reproduced test transferred a hero while its modal was visible, then successfully called the old manual/Auto callbacks. The fixed facade revalidates the original effective controller every waiting frame and at either callback. The runtime separately snapshots each planned actor's controller at collection and checks it before native execution, including an automatic fallback. A transfer at any of those boundaries retires the exact owned modal/waiting message, halts the coordinated session, and leaves the room without consuming the suspended die. The native and transport suites cover the distinct timings; the failing old-source transcript is retained in `tests/network-transport/regression-before-controller-transfer.txt`.

The old bootstrap accepted an old Hello/Welcome/Start transcript before hearing the current host, binding a fresh participant to a stale epoch. Wire version 2 gives every protocol participant a fresh nonce. HandshakeReady, Welcome, WelcomeAck and Start acknowledge a digest of the session, exact profile/roster and every sorted actor/nonce pair. A fresh participant cannot acknowledge the old transcript. Before any welcome or completed roll, a new host Hello can replace a provisional stale session and clear its bootstrap votes and packet caches. An established session refuses rebinding. The protocol tests reproduce the old failure and recovery, with the failing transcript in `tests/network-protocol/regression-before-stale-bootstrap.txt`.

Profiles now include the enabled state and the wire version. Enabled and disabled participants cannot agree on one profile. Initialization advertises only after native patches and the window are installed and Enabled is true; any initialization failure still independently disables and rolls back the transport, window and patches. The production Plugin lifecycle fixture reproduces the previous enabled-state ordering failure and tests rollback after the fix.

`tests/network-end-to-end` connects the production protocol, transport, facade, RuntimeRolls, broker, scratch scope and scheduler in independent peer processes. Native raw/static/actor dice, Lucky/damage rerolls, HP-pool sums, deterministic state restore/record and TA.Run are copied from the exact original IL. Ordinary and Karmic rooms cover owner-only prompts, advantage, Sleep, damage traits, static bonuses, synchronous concentration fallback, Auto during a replacement prompt, exact native draw counts and agreement of the next automatic die. Four additional connected failure rooms cover mismatched profiles/controllers, a pending controller transfer and a different native result. The gateway, GUI, upstream action driver/planners/descriptors, controller service and Unity RNG external API are explicit fixtures; the test is not a full scene or a live Photon/Windows session. Independent suites qualify the original planners, descriptors, await owners, rest command/callback and physical-input boundaries. Full live acceptance remains required.

## 0.5.0.0 single-player additions and multiplayer isolation

The new dialogue/gadget outer await sites are registered as single-player only: `RuntimeRolls.PrepareNativeRoll` returns no wait for them while networked, so the coroutine continues exactly as in 0.4.0.1 and the game rolls. Deferred concentration, travel and camp rolls check `Plugin.Networked()` before deferring and again on every queued frame; a session that becomes networked replays any queued original with game dice on the next frame. The local hold in `NativeNetworkScheduler.BeforeRun` and the world-clock hold apply only when not networked. The multiplayer profile fingerprint and wire protocol 2 are unchanged; the artifact hash in the profile keeps 0.5.0.0 and 0.4.x peers from sharing a room. (Superseded in 0.6.0.0, below.)

## 0.6.0.0 extended rolls in multiplayer

With the shared `MultiplayerExtras` profile setting, outer sites (dialogue, gadget check/save, surprise attack, turn-end stealth) take part in the ordinary await protocol, and deferred synchronous rolls run as their own native step: every peer skips the same void original at the same deterministic point and queues it in the same order. While anything is queued, `NativeNetworkScheduler.BeforeRun` holds every TA coroutine except the front entry's runner, banter is held, and the battle state machine and world-map clock are skipped. The runner probes and plans inside its own `TA.Coroutine.Run`, so `CollectNetwork` claims it; after the agreed faces the original is replayed inside `EnterNative`/`ExitNative`, its void result is observed, and the after-run hook starts the completion comparison before the runner releases the hold. A failed session keeps everything held until the room is left; leaving the room finishes a queued original locally with game dice. The profile fingerprint now includes `MultiplayerExtras` and every per-type setting (`Concentration`, `Downtime`, `Lore`, `RepeatSaves`). The connected-process suite runs this pattern in two- and three-peer rooms with the actual protocol, transport, broker, RuntimeRolls and scheduler, and checks that a held coroutine never advances while a deferred step is pending.

## 0.7.0.0 additions in multiplayer

The new synchronous rolls (the deferred start of a battle turn, lingering effects, recurring condition damage, damage-triggered condition saves, travel crafting) use the same deferred runner, so with `MultiplayerExtras` every peer skips the same call at the same point and replays it inside one shared native step. A deferred turn start skips the pinned tail of `GameLocationBattle.NextTurn`/`StartFirstTurnOfRound` on every peer; while it is queued the battle `Update` and state machine are held, so no peer can begin the turn early. Composite parts are planned on every peer from the same native state and consumed in the original order; their face vectors go through the ordinary ordered agreement. The new outer sites (stealth after an action, spell slot preservation) skip unresolved calls before any protocol exchange so ordinary casts and actions create no rendezvous; the Deflect Missiles site is an ordinary registered await. Spell failure, turn-end stealth and hidden-object Perception wait through `PrepareDeferredRoll` inside their own coroutine. Character-screen rolls (ability scores, level-up hit points) never run while networked. The profile fingerprint now also includes `LingeringEffects`, `Features`, `Stealth`, `CharacterCreation`, `DamageSaves`, `HiddenPerception` and `LevelUpHitPoints`, so peers with different selections cannot share a room.

## 0.8.0.0 additions in multiplayer

Every new roll uses an existing mechanism: traps and noisy objects wait through `PrepareDeferredRoll` inside their own equivalent functor coroutine, turn-start recharge and behaviour dice are parts of the deferred turn start, lingering hazards use the deferred lingering-effect step, Dispel Magic, the Bardic penalty die and an item's last charge are planned inside calls that are already deferred or awaited, and attack modifier dice are part of the ordinary attack descriptor. No new packet type or wire change was needed; the protocol stays at version 2.

- **Conditional groups.** Every peer plans the same groups. Groups are collected in order and each prompt's faces are agreed before the next group; a group's condition reads only faces of earlier groups that every peer has already agreed, so all peers skip the same group; the owner is never prompted for dice a failed check makes unnecessary.
- **Ready actions.** `OnReady` runs on every peer after the agreed faces are applied and before the original resumes, so the rewritten attack modifier is the same everywhere and is then covered by the completion comparison.
- **Game-master dice.** A master leaf has no character owner. `AskNetwork` gives it to the host (the room's game master); `NetworkOwners` excludes it from the per-character controller checks so a host-entered die cannot be refused as an ownership mismatch, while the descriptor and face vector still include it.
- **Proxies.** `MultiplayerRolls.OwnerActor` maps a spell effect proxy to its controller before ownership is resolved, so the controlling player is prompted and every peer agrees on the owner.
- **Profile.** The fingerprint now also includes `Traps`, so peers with different trap settings cannot share a room. UI-only settings (roll history, panel position, folded sections) are excluded.
- **Waiting banner.** Non-owners show the owner's player name, character and roll while waiting; it is display only and reads protocol state without changing it.

The connected-process suite adds an `extended` scenario in a three-peer room: a conditional group taken on success and skipped on failure, hero dice followed by host-entered master dice in one vector, a ready action rewriting a call argument before resume, a master-only roll and an ordinary d20 afterwards. Every peer must observe the same faces, skips and rewritten values.

## 0.8.1.0: the first live two-player session

**Evidence.** Both players' Windows logs from a 0.8.0.0 session (2026-10-07) agree on 48 shared steps: surprise, monster identification, initiative, wolf attacks, a bite's save and damage, and a Sleep spell whose 5d8 pool the host entered. At sequence 49 both computers reached the same site (`CharacterActionAttack/<ExecuteImpl>d__7:RollAttackMode:034b`, a wolf's attack, owner = host, no manual dice on either side) about 6.8 s after the previous step, but with different action keys. The host, as master, halted ("Native roll descriptors disagree between players."). 0.8.0.0 then left the Photon room and threw `InvalidOperationException` from `CollectNetwork` into the game's action coroutine. The game shows "Mod Warning! … instability" for any logged exception while mods are loaded (`TacticalAdventuresApplication.HandleLogModException`). The client saw the room disappear and halted as well. Neither log shows the game's own GUID desync check (`RulesetEntityManager.CheckCurEntityGuidByTick`).

**Cause (reproduced).** `CharacterActionAttack.ExecuteImpl` uses its locally computed `ActionModifier` only when `GameLocationBattleManager.CanAttack` succeeds. That check depends on the attacker's perceived foes, positions and line of sight. Otherwise it uses `ActionParams.ActionModifiers[0]`, the copy the acting player's game sent. `TrendInfo`'s network serializer keeps the value, source type, additive flag, source name, details and a `RulesetCharacter` source only. It drops a feature or condition source (for example Pack Tactics or Prone), the die flag and the die type. The 0.8.0.0 descriptor wrote every `TrendInfo` field and every `RulesetAttackMode` field, so the same native roll had two descriptions. `tests/network-descriptor/regression-before-network-copy.txt` keeps the old descriptor's failing result for the new case. A random-state difference cannot be fully excluded from these logs, because 0.8.0.0 logged only whole-descriptor hashes. 0.8.1.0 logs per-part hashes (below), so a recurrence will name the differing part.

**Changes.**

- *Descriptors use what the game sends.* A `TrendInfo` is described by its network-serialized fields. A `RulesetAttackMode` is described by the game's own network identity (`IsComparableForNetwork`), by which the receiving game finds the attack mode in its own list. `CharacterActionParams` is described by its serialized fields, without the hover position, the float parameter, the staging flag or the target action. `ActionModifier.failureFlags` (UI text) is excluded. Values that change a roll (trend values, roll modifiers, the attack mode's to-hit bonus, actors' health, attributes and conditions, and the random state) are still compared; the descriptor suite checks both directions.
- *Attack modifier dice are found from synchronized data.* `AttackBonusDice` no longer reads `dieFlag`/`dieType`. A to-hit trend is a Bless-style die when its source type and name match exactly one die-valued combat affinity of the attacker (from `EnumerateFeaturesToBrowse` origins), and no other to-hit trend has that source. The die and its count come from the affinity. The plan is the same whichever copy of the modifier a computer rolls with.
- *A plan-only difference uses the game's dice.* The admission rendezvous sets the protocol's existing `AllowAutomaticOnMismatch`. When every player has the same action key (native call and random state) but a different local plan (signature), the master proposes the automatic decision and play continues.
- *Failures pause; they never stop the room.* `MultiplayerTransport.Fail` halts the protocol (the halt still reaches the other players) and marks the session paused. It no longer calls `LeaveRoom`. While paused, `NativeNetworkScheduler` holds no coroutine and no banter. An unexpected deterministic draw during a barrier pauses and releases the hold instead of throwing. `RuntimeRolls.Prepare` returns no wait, and `DeferredRolls` defers nothing; a queued entry not yet shared runs with the game's dice. Every former `throw` on a multiplayer path inside a game coroutine or patched native method is now a pause with the game's dice. That covers admission, prompts, handoff, owner validation, argument validation, result observation and completion. A roll already handed off with agreed faces keeps those faces. `MultiplayerRolls.Update` releases any remaining hold, and the UI shows a 20-second "Manual dice paused" notice; the settings panel shows the reason. A location load or exit (`GameLocationManager.EnterLocation`/`ExitLocation`, `GameManager.DestroyGame`) or a roster, host or profile change starts a fresh session once no roll is pending.
- *Diagnostics.* Each admission logs `roll_descriptor` with 8-character hashes of the random state and of each argument. An actor is split into `.hp`, `.attributes`, `.conditions` and `.proficiencies`. A descriptor disagreement logs both players' action key, signature, owner and dice in the `halted` line's `detail`.

**Limits.** A pause is not a resynchronization. If the games had really diverged (for example a Bless-style die rolled again by one computer's local `CanAttack` evaluation while the other used the sent modifier, which also differs in vanilla), the game state may differ until the players load a save together. Live two-player acceptance of 0.8.1.0 is still required.

## 0.8.2.0: agree on the dice, not on each game's state

**Evidence.** Second live two-player session (0.8.1.0, 2026-10-07): 32 shared steps agreed (surprise, two identifications, eight initiative rolls). At step 33, the first attack by an enemy (no entered dice on either computer), the host as master paused manual dice with both descriptions in its `halted` line. The `roll_descriptor` parts of the two computers were identical except two: `rng`, the attacker's `hp`/`attributes`/`conditions`, the target's, `toHitTrends`, `advantageTrends` and `rollModifier` were all equal, while `attackMode` and `attackMethod` (the attack mode's source definition) differed. Both games held the same random state and the same characters but carried different attack modes for the same action. The game sends an attack mode as an index into the acting character's own `AttackModes` list (`CharacterActionParams.SerializeAttackMode`), which is rebuilt from pooled objects whenever attack modes refresh (monster attack sequences via `UsedMainAttacks`, `HandleActionExecution`, `ResetVariables`). That makes this the game's own synchronization. The mod's barriers change coroutine timing relative to the game's tick-scheduled commands, so an influence on when the lists refresh is not excluded.

**Change.** The players no longer agree on each game's state. They agree on:

- *the roll's identity* (`NativeNetworkDescriptor.Identity`): the site, the native method and the characters taking part (receiver and character arguments, by GUID);
- *the dice* (`Signature`): the identity plus every planned die's owner, die, count, context, advantage, proficiency, reroll features and group order.

Same identity, different dice: the existing automatic relaxation lets the game roll for everyone. A different identity at the same sequence (two computers at different rolls) still pauses, as do prompt, owner and profile mismatches. After the native step the players still finish together and compare `CompletedSignature` (return, outputs, characters, random state, dice used). The completion rendezvous now uses `AllowAutomaticOnMismatch`: a difference becomes the "differs" decision, logged as `results_differ` and shown once per session as "Games differ" after a roll with entered dice. It never pauses. `roll_descriptor` keeps the full state key and parts, and adds readable names of definitions and attack modes. `roll_result` logs the result parts.

**Consequences.** Each game applies the agreed faces with its own state. If the games' states differ (the game's own desynchronization), their results can differ; the mod reports this instead of stopping manual dice, and players should load a save together if their screens disagree. The connected suite now has a `different-result` room: 18 differing results are reported on both peers, and no peer pauses. Its three remaining failure rooms (different profile, different owner, controller transfer) pause without leaving the room.


## 0.8.3.0: shared rolls between two ticks

**Cause.** The 0.8.2.0 note above left open whether the mod's barriers influenced the attack-mode difference. They did. `NetworkingManager.FixedUpdate` computes `frozenGameplay = tick.UpdateTimeManipulation() <= 0f` and, when not frozen, increments the local tick, runs the delayed commands scheduled for that tick (`ExecuteActionRPC` and the other action RPCs) and the deterministic local commands. `NetworkingManager.Update` recomputes the same flag. The gameplay managers (action, battle, AI, character, location, quest, banter, the game state machine) run only when `NetworkingDefinitions.CanUpdate()` holds: in multiplayer, a fixed step with gameplay not frozen. The mod held the owning action coroutine (and every other TA coroutine) while players decided a roll, but ticks kept counting and the scheduled commands kept running. Each computer released the hold at its own wall-clock moment, so a tick-scheduled action could resolve its attack mode index against a list another computer had or had not yet refreshed. Both live sessions diverged right after such holds (after the Sleep pool, after the initiative rolls).

**Change.** `NativeNetworkScheduler` patches `NetworkTick.UpdateTimeManipulation` (IL SHA256 `4b3c0c0c5cd4c13fbd30059a5209fdd055afb29a6e26f76f1202b52e226ed5f7`; only callers `NetworkingManager.Update` and `FixedUpdate`; foreign patches refused) with a postfix that returns `0` while `RuntimeRolls.FreezeTicks` holds:

- from the native run that reaches a shared roll until it is decided (`NetworkGate` registers the wait; `PumpNetwork` advances it once per rendered frame, outside the game coroutine);
- from the native call's exit until the shared completion comparison ends;
- while multiplayer deferred rolls are queued (they replay between two ticks).

The await's coroutine is recorded at the first decision step inside its native run and claimed explicitly (`Claim(owner, coroutine)`), so a decision finished outside the run still binds the right coroutine. The gate always yields at least once, so the native call never runs in the tick that reached the roll: every computer runs it at the next tick. Once nothing is pending, the postfix keeps reporting a stopped tick until it is called inside a fixed step (`Time.inFixedTimeStep`), where `FixedUpdate` decides whether that step runs a tick; the per-frame recompute in `Update` never resumes ticks between steps. This keeps the resumption tick identical under either script order of the network manager and the gameplay managers. Pausing, leaving the room, a reset or an unavailable fixed-step answer clears the stop.

**Consequences.** All computers stop at the tick that reached the roll and resume from the next tick, so tick-scheduled commands meet the same game everywhere. The game's own wait-for-players logic is unaffected: peers stop at the same tick, so neither runs ahead far enough to trigger it. The game's tick buffer timing is not inflated (its waiting time counts only its own dilation). A deterministic draw inside a game tick while a roll is held is now lockstep and allowed; one outside the ticks still pauses manual dice. A deferred roll reached outside the owner's run while another shared step is pending keeps the game's dice. Pause transitions (an asynchronous halt) can still land on different ticks; the completion comparison and "Games differ" notice remain as a safety net. The connected suite models ticks with a random 0-3 fixed steps per frame per peer and other gameplay drawing game dice every tick: every shared roll ran at the same tick on every peer, while a control room that ignores the stopped ticks diverged on all 18 steps.

## 0.8.4.0: definitions by name

**Evidence.** Third live session (0.8.3.0, a custom campaign): 223 roll descriptions and results matched on both computers in random state, characters, health and native results. Eight differed only in the hash of an attack mode's source definition (`Attack_Wolf_Bite` on both) or of a saving throw's effect forms. A second wolf variant with the same attack name matched.

**Cause and change.** `UserCampaign` assigns every user-content definition (monsters, NPCs, items, merchants, loot, quests and more) `SetUserContentGUID(Guid.NewGuid().ToString())` at load, independently on each computer. `BaseDefinition.SerializeDatabaseReferenceForNetwork` sends only the definition's name, and the receiving game looks it up by name. The descriptor wrote name and GUID for every definition and for each condition's definition; it now writes the name only (its type is written before it). The earlier live attack-mode differences (0.8.1.0 and 0.8.2.0 sessions) were in the same campaign and are most likely the same artefact; the tick lockstep of 0.8.3.0 remains necessary independently.

## 0.8.4.1: naming a peer's halt

**Evidence.** Fourth live session, host log: every session with the second player (in the lobby and after each of four location loads) stopped within 1.5 s of `session_joined`, before readiness or any roll, as "A room member stopped the synchronized multiplayer roll." A follower binds to the master's session on the master's first `Hello` and compares profiles there; on a mismatch it halts and broadcasts a `Halt` before the master ever processes the follower's `Hello`, so the master only learned that someone stopped.

**Change.** `Halt` packets already carry `Hash(reason)`. `MultiplayerProtocol.KnownHaltReason` maps the digests of every fixed reason (this and earlier builds) back to text; the receiver halts with "Another player's game stopped manual dice: <reason>" or, for an unknown digest, the generic reason. A profile mismatch records both profile digests in `FailureDetail`; a roster mismatch has its own reason. The UI shows a mismatch as "MANUAL DICE OFF" with what must match, notices a repeated reason at most once per ten minutes, and the settings status explains the fix. No packet format changed.

## 0.8.4.2: pooled damage form breakdowns

**Evidence.** Fifth live session (0.8.4.0, matching settings): 264 roll descriptions and results agreed in random state, characters and native results; three differed only in effect forms (Giant Crow talons, a spell save).

**Cause and change.** `EffectForm.Copy` obtains its damage form with `DamageForm.GetCopy`, from a static object pool; `DamageForm.Copy` neither copies nor clears `damageBonusTrends`, the tooltip breakdown read only by `GuiEffectsFormater`. A reused pooled form keeps whatever an earlier local use left, so its contents depend on each computer's own history. The descriptor skips that field; every other field of the damage form is still written.
