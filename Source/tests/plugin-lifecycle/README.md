# Production Plugin lifecycle boundary tests

Run `python3 tests/plugin-lifecycle/run.py` from the extracted source root.

Latest verified result: **27 cases, 193 assertions, 0 failures**. The complete hardening source also compiled separately as a library against the genuine pinned game, UMM 0.32.4, and Harmony 2.3.6 runtime references; the compiler output is `build/real-dependency-compile.txt`.

The runner captures the production `Plugin` and `ModSettings` classes verbatim from `src/Plugin.cs`. It removes only the separately owned `InputGuards` class from the test compilation and supplies a test boundary for that installer. Production source bytes and captured-class bytes are identified by `source-manifest.json`.

The tests use the genuine supplied game assembly and Unity metadata references, including the real file hash consumed by `GamePreflight`. Loader settings/callbacks/logging, UI creation/teardown, runtime cleanup, patch installers, and Unity runtime metadata are mocked. `HarmonyBoundary.cs` is an explicitly test-only owner bookkeeping model with injectable `UnpatchAll` failure. It performs no detours. The harness initially attempted genuine .NET 8 Harmony detours, but the host could not locate the CLR JIT through Harmony's detour backend; this fixture therefore does not claim actual Harmony patch removal behavior.

The cases exercise failure after each installer, failure after callback assignment during window creation, independent runtime/UI/unpatch cleanup failures, disabled and loaded flags, callback restoration, preservation of foreign and fault compatibility owners, restart blocking after a failed patch rollback, safe disabling, refused unload with continuation patches retained, null/throwing settings, logger faults, and diagnostics metadata failure.

The diagnostics case parses the actual production `MDR_DIAGNOSTICS` JSON with an independent JSON parser. It verifies release version, loaded fixture assembly paths/hashes, loaded boundary versions, escaped Unity-version text, UTC recency, Mono detection, pointer width, and CLR version. Test UMM and Harmony assemblies are boundary models, so their test markers are **not** evidence of genuine loader execution. The marker is emitted only after completed installation, UI creation, and enabled/loaded state. Live Windows/Solasta process correlation and manual scenario evidence remain separate.

These tests do not execute a Unity renderer, the game engine, UMM's real settings loader, real detours, suspended native iterator continuations, or Windows/Unity Mono loading. Results demonstrate production lifecycle control flow under the stated boundary behavior. Genuine build/reference validation and in-game runtime evidence provide separate checks.

The settings cases check that every serialized `ManualDiceRollerSettings` field keeps its name and default (an older `Settings.xml` loads with the new UI-only defaults), that each settings-page preset ("Everything manual", "Party dice (recommended)" = the shipped defaults, "Combat only", "Minimal") sets exactly its roll types while leaving the window, notice, history and multiplayer options alone, that the active preset is recognised, and that the production multiplayer profile fingerprint lists exactly the roll types plus "Use these in multiplayer too" and none of the UI-only window, notice or history settings. The fingerprint case reads (does not compile) `src/MultiplayerRolls.cs`; its hash is recorded in `source-manifest.json`. The IMGUI drawing of the settings page itself needs the live loader.

The multiplayer lifecycle additions mock service lookup and Photon room flags rather than invoking Unity internals. They qualify scheduler-install rollback, independent transport initialization/shutdown failures, refusal to toggle or unload inside a joined room, and UMM update pumping of transport and native completion. Leaving a room permits the existing disable path. These checks do not establish real Photon connection or room teardown behavior.
