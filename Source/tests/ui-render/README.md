# Production window boundary tests

Run `python3 tests/ui-render/run.py` from the extracted source root.

Latest verified result: **72 cases, 396 assertions, 0 failures** against the production source hash recorded in `source-manifest.json`.

The runner compiles the complete, unchanged production `src/RollWindow.cs` with C# 7.3 and a .NET 8 test host. `UnityStubs.cs` provides a deterministic fake Unity boundary; `BoundaryStubs.cs` supplies only the test cursor, Plugin, and RuntimeRolls facades. These stubs are test-only and are never included in the mod DLL. The separate Unity stub file is reusable by the native reset integration harness.

The tests invoke the actual private `OnGUI`, completion, focus, and destruction methods. They exercise raw-face controls, Confirm/Auto/Enter/Escape callbacks, cursor ownership, owner-specific closing, logical header drag events, callback failure, successor prompts, malformed persisted layout, long text/large requests, and injected faults during startup, persistence, input capture, and rendering. A one-time third-texture allocation fault also verifies that the next prompt can render after partially completed style initialization. The GUI boundary records control rectangles, enabled state, field edits, scroll nesting, labels, and hot control ownership.

Rendering faults are expected to close only the current owner and invoke its native completion callback. A callback fault should then reset the runtime. Close-time capture, persistence, and cursor errors must not prevent state cleanup or callbacks. Failed capture polling should preserve a previously captured held press through its release.

`GUIUtility.hotControl` access is deliberately restricted to the simulated GUI context as an adversarial lifecycle boundary. The actual Unity 2019 managed getters/setters call native `Internal_GetHotControl` and `Internal_SetHotControl` directly; their managed bodies do not contain an `OnGUI` check. Therefore these tests do **not** prove that the real engine throws on outside-GUI access. The test checks resilience to that simulated boundary.

The fake Unity Object implements destroyed-object `== null` semantics while preserving managed reference identity. Its engine-destruction boundary deliberately marks a component destroyed before invoking `OnDestroy`. This defensive dead-native-reference scenario verifies that managed cursor/callback cleanup still runs and a successor prompt survives. It does **not** establish the exact order in which real Unity retires native objects and invokes lifecycle callbacks.

The host does **not** exercise a Unity renderer, the real game cursor service, a physical mouse, Unity's native event routing, scroll-coordinate transforms, font glyphs, text wrapping/clipping, or native pointer capture semantics. It validates production control flow and state/callback ownership under explicit fake-boundary behavior. Real visual readability, physical dragging, focus changes, world click-through, and cursor behavior still require in-game playtesting.

`results.txt` records the latest run. `source-manifest.json` identifies exactly which production source and test boundaries were compiled. Generated assemblies and compiler responses are in the local `build` directory.

Multiplayer owner prompts require the internal network authorization overload; the public three-argument API still uses the native fallback in multiplayer. Authorization is request-local, retires on close, and cannot be inherited across an offline-to-room transition. A nonowner waiting banner renders the request title and controlling-player message without controls, cursor acquisition, callbacks, or pointer/key capture. An active owner modal takes precedence, stale banner closes preserve later requests, and a cosmetic banner-render fault leaves network completion untouched. These are fake-boundary control-flow checks, not actual multiplayer/Unity UI certification.

The 0.8 UI cases cover colour coding, the session roll history and the waiting banner. The GUI boundary additionally records each control's style, tint and texture so the tests can read colours back. Every `RollKinds` value has its own accent and badge label, the accents are pairwise distinct, and both the accent (≥ 3:1) and its lighter text tint (≥ 4.5:1) keep contrast against the panel. A prompt's kind colours its badge, title, cap/title rule, active die outline and silhouette, and running total; the badge sits between the title and the options button and is never drawn as a text box (so it never counts as a chip). Kind textures are created once per kind, a partial allocation fault releases what it made, and everything is released with the window. The history records confirmed faces, "Let the game roll" (completed by the game's d20 notice), the game's own d20s and other players' agreed faces, newest first and capped at forty. The panel opens from the • • • menu, lists rows newest first with kind-coloured results, scrolls drawing only visible rows, clears, closes, drags and remembers its place, keeps malformed stored places on screen, and closes on a drawing fault. It blocks only gestures that start over its own rectangle (a captured press stays captured through its release, a stale hover never blocks, keys always pass), leaves the modal capture untouched, and never takes a fresh gesture that starts over the modal window above it. The waiting banner shows the request title, dice and target, the controlling player's message with an animated ellipsis and the kind colour, at the top centre, without input, and inside a narrow screen. Game notices carry the kind colour. The running-total expectation changed with the 0.8 layout: the count ("2 of 3 dice") and a larger kind-coloured "Total 7" now share the band under the dice.

The owner body now calls the genuine Unity `GUIStyle.CalcHeight(GUIContent,float)` API for every message row. Moderate wrapping expands rows; very long content scrolls within a bounded text viewport above the independent dice viewport, while the header and completion controls remain visible. Label styles explicitly clip to their allocated rectangles. The metric fixture uses a declared character-width/line-height approximation, not native font measurements. It proves that production layout consumes measured heights, keeps successive content rows disjoint, separates both viewports from the footer, and retires the owned prompt on throwing/nonfinite metrics. `baseline-long-text-failure.txt` records the old fixed-row allocation failing under that same explicit metric boundary. Physical font rendering and scroll-coordinate behavior remain live acceptance cases.
