# Native rest regression fixture

Run `python3 tests/rest-native/run.py` from the extracted source project root. The script requires the supplied pristine managed files and pinned .NET8/Harmony test dependencies. It compiles the current production RestPatches, RuntimeRolls, and RollBroker sources.

The fixture executes actual pristine `HitDiceRestItem.OnRollCb`, `LocalCommandManager.RollHitDie`, `RulesetCharacterHero.RollHitDie`, `ComputeAndApplyHitDieRoll`, and native callback state changes. Current result: 125 assertions passed.

Covered: raw Constitution healing; advantage on both the base die and every rest bonus; flat-bonus carry into the first dice bonus; native bonus ordering, clearing, and events; one spent die and one final callback; highest available multiclass die selection; maximum-hit-die game setting; closing/rebinding/destroying a rest item; lifecycle reset; changed HP, Constitution, class, pools, bonuses, or advantage features while a prompt is open; disabled-mod cancellation; an event-triggered nested native draw that cannot consume the pending bonus face; unbind/rebind/same-hero rebind/destroy/reset during the executing native callback; unchanged native scratch collections and live enumerators; and disabling only HitDice before or after acceptance while SpellPools remains enabled. Category cancellation completes one automatic native rest roll rather than consuming the accepted manual face.

Environment isolation is explicit: a fake modal submits real broker tickets; the driver is stepped directly because Unity scheduling is unavailable. Unity item objects have a test cached pointer. The terminal ReceiveHealing method records/applies health in the fixture. The native callback retains its original state mutation. Its Refresh call is replaced with the exact original initial character field access and MaxHitDiceCount call instructions, preserving the stale-binding failure while isolating Unity rendering. RefreshRollButton rendering is removed. A fixture-only baseline temporarily unpatches the new callback guard to reproduce the original NullReferenceException after native healing and spending; the guarded lifecycle cases then execute without that failure. Unity Mathf.Max(int,int) is replaced with identical System.Math.Max to avoid its Unity ECall initializer. The helper’s native-RNG fallback is replaced by a counted test draw for the nested-notification case; this is not a test of the game’s RNG implementation. Unrelated effect/save planners are disabled because this fixture is scoped to rest.

The fixture does not certify Unity UI rendering, real StartCoroutine/StopCoroutine scheduling, Bind/Unbind UI rendering, or external mods. The production plugin separately compiles against the actual Unity/Mono/UMM/Harmony dependencies, and rest preflight pins seven original native method hashes plus the required fields.

The common resolver accepts `MANUALROLL_TEST_MANAGED`, `MANUALROLL_TEST_DOTNET`, `MANUALROLL_TEST_SDK_ROOT`, and `MANUALROLL_TEST_REFERENCES`, or corresponding runner options. `python3 tools/FetchDependencies.py` obtains the exact official test/build references; it does not require an Unfinished Business archive. Sources compile from byte snapshots; pre/post source and native game/Harmony hashes must agree for a passed manifest.

The replicated rest producer is also tested at `RestHitDice.Network`, the native `LocalCommandManager.RollHitDie` call reached by `NetworkingManager.RollHitDieAsync`. These cases use actor-only capture and revalidation, preserve advantage/base/bonus faces and native callback/spending, and retire accepted faces after a changed hero snapshot. The harness executes that preserved command directly in an offline host; it does not establish Photon RPC delivery or a live multiplayer session. The separate network fixtures qualify protocol, transport, scheduler and replicated-runtime integration.

A startup-boundary regression substitutes only the Unity `StartCoroutine` call. It injects failure both before the driver advances and after the original native command completes. The prefix retries only the former, proving that late startup errors cannot cause a second spent die or duplicate callback. This is adversarial scheduling-boundary control flow, not evidence that Unity normally throws after completing startup.
